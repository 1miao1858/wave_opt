# 业务确认问题清单(POC 阶段)

> 来自 2026-07-23 数据盘点 + POC spec 对照
> 文件名已规范化:`作业_YYYY-MM-DD.xlsx` / `库存_YYYY-MM-DD_日报.xlsx` / `库存_YYYY-MM-DD_HHh.xlsx`

## A. 数据完整性(P0,阻塞 POC 跑通)

### A1. 加工 vs 非加工 在哪区分?

POC `sub_problems` 要按 `wave_type: 加工 / 非加工` 拆开跑,但 5 个作业数据文件里:
- `任务类型名称` 只有「普通出库 / 二步移库」
- `业务类型名称` 全 NaN
- `提总模式` 全是 `2.0`
- `单据状态名称` 只有「拣货完成 / 移库完成」

→ 请业务给一个**能区分加工 / 非加工的字段或规则**(订单号前缀?波次号前缀?SKU 主数据里某列?)

### A2. 大小件分类(le_20 / gt_20)用什么衡量?

POC `size_class` 要按单的件数分 ≤20 件 / >20 件,还是按单的 SKU 数?
用 `分配件数` 还是 `拣货数量`?跨 SKU 合并算吗?

### A3. 7-20 的 14 / 15 / 16 点库存快照能不能补?

没有 14h-16h 的中间状态,7-20 这天只能用 13h→17h 4 小时大间隔跑扫描,或干脆跳过 7-20 的整点扫描。

## B. 字段映射(P0,阻塞 POC 跑通)

### B1. 货架粒度取哪一级?

容器三级结构:
- 外层容器编码(S001…,72 个)= 仓储区
- 上级容器编码(S001-A-9-1…,3940 个)= 货架层 ← **推荐这个**(货到人整层取货粒度)
- 容器编码(S001-A-9-1-05…,37725 个)= 单个货位

→ 确认用「上级容器编码」吗?最细的容器编码会让 MIP 规模从 ~37K 变量爆到 ~370K 变量,Gurobi 撑不住。

### B2. 订单的 timestamp 用哪个时间?

作业数据有三个时间字段:
- `创建日期`:订单创建时刻(POC spec 推荐)
- `拣货开始时间`:拣货员实际开始拣货
- `拣货完成时间`:拣货完成

→ 确认用 `创建日期`?

### B3. 拣货件数用 `分配件数` 还是 `拣货数量`?

抽样里两者都是 3,但有些行可能有 `拣货缺货数量` > 0。POC 用 `分配件数`(应拣数)还是 `拣货数量`(实拣数)?

## C. 数据范围(P1)

### C1. 5 天作业数据够不够?

POC spec 假设 200 单/日,5 天 = 1000 单。如果只是 POC 验证算法正确性,够用;如果要跑生产 representative 数据,可能要 2 周+。→ 确认 5 天够?

### C2. 日报 20000 行的 7-18 和 7-23 是不是被截断?

其他日报都是 ~37000 行,只有这两个 20000 行。是不是系统导出时被截了?需要补完整的吗?

### C3. 7-18 日报的记录时间范围(7-16 17:23 ~ 7-17 23:36)是正常的吗?

这意味着 7-18 的「日报」其实记录的是 7-16/7-17 的库存变化,不是 7-18 当天的。这种"日报滞后一天"是 WMS 系统行为还是导出 bug?

## D. POC 假设核对(P1)

### D1. N_max=50(单子波最大订单数)在 5 天数据里有代表性吗?

5 天平均拣货 3500-5000 行/日,按 POC spec 假设平均每单 4-5 行,折 ~700-1000 单/日。N_max=50 → ~15-20 子波/日。→ 业务看这个量级合理吗?

### D2. 日截单 14:00 / 日截止 18:00 对得上实际作业时间吗?

抽样里拣货开始时间最早 09:05,最晚到次日 00:32(7-19)和 03:05(7-22)。意味着作业会跨夜——截单 14:00 是不是只截白天单,夜单算次日?→ 需要业务确认。

### D3. K_ws=8(每窗口机器产能 8 件/小时)对吗?

spec 写死的,业务确认这个产能数字对吗?如果实际机器产能不是 8 件/小时,Filter 3 的利用率算不准。

## E. POC 不在范围但要业务拍板(P2)

### E1. 跨窗口延迟订单

POC 简化成"窗口订单要么进子波要么缺货剔除"——业务接受这个简化吗?还是 POC 也要支持订单延迟到下一窗口?

### E2. 库存分布 / 货架重排优化

POC 不做(独立后续项目)——确认这个边界?
